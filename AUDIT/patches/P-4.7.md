# Patch — P-4.7 (RLS Policies Tarefas)

**Motivo:** a frase "CRUD em tarefas dos workspaces que tem acesso" pressupõe um modelo de
membership que nenhum prompt cria (resíduo dos workspaces custom removidos em D-5); a coexistência
com "vê apenas tarefas atribuídas a si ou criadas por si" é contraditória com "comentários visíveis
para todos no workspace" (comentário visível de tarefa invisível). Também: CS-3 (número).

---

## Escopo

### ANTES

```
RLS para schema tarefas. Super_admin: full access. Colaborador: CRUD em tarefas dos workspaces que
tem acesso; vê apenas tarefas atribuídas a si ou criadas por si. Diretor: SELECT em todos os
workspaces (para TreeView de despacho); recebe approval_requests. Demais: sem acesso.
```

### DEPOIS

```
RLS para schema tarefas (semântica fechada — sem membership por workspace, ver P-4.6):
- Super_admin: full access.
- Colaborador: SELECT em todas as tarefas dos 6 workspaces (transparência interna — necessário
  para kanban/lista do workspace); INSERT em qualquer workspace; UPDATE/soft-DELETE apenas em
  tarefas que criou ou nas quais é assignee.
- Diretor/conselheiro: SELECT em tudo (TreeView de despacho); UPDATE apenas em approval_requests
  endereçados a si; NÃO recebem tarefas operacionais (BRAIN §6.9) — sem INSERT de task própria
  atribuída a diretor.
- Comentários/anexos/time_entries: seguem a visibilidade da tarefa; escrita do próprio autor.
- Demais papéis (submissor, aluno, hospede, ouvinte): sem acesso ao schema.
```

## Arquivos permitidos

```
ANTES:  - packages/db/src/migrations/0011_tarefas_rls.sql
DEPOIS: - arquivo SQL de policies com nome sequencial posterior à migration do kit (G6.4)
```

## Critérios de aceite

### ANTES

```
- [ ] Super_admin: full CRUD
- [ ] Colaborador: CRUD em tarefas que é assignee ou creator
- [ ] Diretor: SELECT em todas as tarefas (para visualização árvore)
- [ ] Diretor: UPDATE em approval_requests (aprovar/rejeitar)
- [ ] Comentários: visíveis para todos no workspace
- [ ] Types passam
```

### DEPOIS

```
- [ ] Super_admin: full CRUD
- [ ] Colaborador: SELECT em qualquer tarefa; UPDATE/DELETE só como creator/assignee (teste com 2 usuários)
- [ ] Colaborador: INSERT em qualquer um dos 6 workspaces
- [ ] Diretor: SELECT em todas; UPDATE apenas em approval_requests endereçados a si (teste)
- [ ] Submissor: zero acesso ao schema (teste)
- [ ] Comentários seguem a visibilidade da tarefa
- [ ] Policies com USING e WITH CHECK separados, deny-by-default
- [ ] Types passam
```
